2. Architecture Review

2.1 Strengths

  • MVVM pure Compose — All Fragments removed, pure Compose Screen + ViewModel. Clean separation of concerns.
  • Koin 3.5.6 DI — 10 ViewModels + 1 Repository via single{} and viewModel{}. Lightweight, no Hilt boilerplate.
  • God Repository Pattern — DeviceRepository orchestrates 12 DataSources with a single coroutine loop. DataSources are replaceable and testable.
  • Multi-level Fallback Chains — CPU temperature 5 levels, battery cycle 10+, battery current 30+ sysfs paths, GPU load gfxinfo fallback. This is production-grade defensive coding.
  • CpuCache chip database — Pre-cached Snapdragon chip data injected via SystemProperties reflection. Elegant lazy-init with targeted field override.
  • SELinux bypass via Binder IPC — Using dumpsys as the mechanism to read protected data through system services. Clever workaround for non-rooted devices.
  • HistoryCache time-series — 11 series with configurable capacity, exposed via MutableLiveData for Compose chart consumption.

3.2 Key Technical Highlights

  • mA → µA auto-detection — abs(value) < 100 heuristic correctly handles OEMs that report in different units. Critical for accurate battery power calculation.
  • Three-level charge detection — EXTRA_PLUGGED → currentNowUA sign → EXTRA_STATUS. Robust against OEM-specific intent field ordering.
  • Dual-cell voltage calculation — effectiveVoltage property in BatteryInfo correctly sums dual-cell battery voltages.
  • GPU DVFS throttling detection — isThrottled = freq < 70% of max is a reasonable heuristic for detecting thermal throttling.
  • GPS multi-strategy — GnssStatus.Callback (API 30+) + GpsStatus.Listener fallback + lock-protected status to prevent location updates from overwriting satellite data.
  • 5G NR/LTE dual signal — Full reflection for parseNr/parseLte to bypass compileSdk 35 Telephony stub limitations. Separate signal fields for NR and LTE.

7. Code Quality Assessment

7.1 Highlights

  • Consistent Kotlin style — idiomatic Kotlin throughout, proper use of scope functions, extension properties, and coroutines.
  • Comprehensive data models — 14 models with 30+ fields each. Well-structured with default values and computed properties.
  • BatteryDataSource is a masterpiece of defensive programming — 50+ sysfs paths with OEM-specific fallbacks and unit auto-detection.
  • GPS lock pattern — synchronized(lastRealStatus) prevents the classic race condition between location and satellite callbacks.
  • CpuCache chip database — Clean separation of chip-fixed vs OEM-variable data. injectCpuInfo()/injectGpuInfo() only override static fields.

7.2 Code Smells

  • BatteryDataSource is 800+ lines — Consider splitting into BatteryTempSource, BatteryCurrentSource, BatteryCycleSource sub-components.
  • DeviceRepository.collectData() is a single 90-line method with 11 sequential runCatching blocks. Could benefit from parallel collection via async/awaitAll.
  • All catch blocks are empty — catch (_: Throwable) with no logging. Silent failures are extremely hard to debug in production.
  • No const vals for string keys — History series keys like "cpu_temp", "gpu_load" are magic strings repeated across Repository and UI layers.
  • FloatingWindowService is 500+ lines — Mixes UI rendering, data collection, service lifecycle. Should delegate to a separate WindowManager helper.
